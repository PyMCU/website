```python
from pymcu.drivers.max7219 import MAX7219
from pymcu.hal.spi import SPI
```

Driver for the **MAX7219** driving an **8x8 LED matrix** over SPI.

:::caution[It is a matrix, not a 7-segment display]
The MAX7219 chip can drive either eight 7-segment digits or an 8x8 matrix, depending on the module
it is soldered to and on its decode-mode register. **This driver is written for the 8x8 matrix.**
`init()` explicitly sets decode mode to `0x00` — raw, per-LED control — and `set_row(row, data)`
takes an 8-bit pattern where each bit is one LED in that row. It does not encode digits, and there
is no BCD/font path.

If you are reading a description of PyMCU's MAX7219 support that says "8-digit 7-segment display",
that description is wrong.
:::

`MAX7219` is a **PyMCU stdlib driver**, not part of MicroPython or CircuitPython — neither
ecosystem specifies a MAX7219 class in its core API that PyMCU could mirror, so there is nothing
to switch between and this page shows a single API. You import it exactly as written above
whichever API you use for the rest of your program: a `machine.SPI` sketch and a `busio.SPI`
sketch both say `from pymcu.drivers.max7219 import MAX7219`, and it compiles to the same code in
both.

:::note[AVR only]
The SPI back end lives in `pymcu.drivers._max7219.spi`. Every register write dispatches on
`__CHIP__.arch` with only an `"avr"` case, so on another architecture the driver compiles to
nothing.
:::

## `MAX7219(spi)`

| Parameter | Type | Description |
|---|---|---|
| `spi` | `SPI` | An initialised `pymcu.hal.spi.SPI` controller |

Construct the bus with the chip-select pin: `SPI(cs="PB2")`. The `SPI` object is a zero-cost
abstraction with no runtime representation — it fixes the bus at compile time and the generated
code drives the SPI registers directly.

:::caution[Chip select is the hardware SS pin]
On AVR the driver's register-write helper is a shared subroutine that toggles **`PB2` directly** —
the ATmega328P's hardware `SS` pin. Passing a different `cs=` to `SPI()` will configure that other
pin as an output, but the MAX7219 writes will still strobe `PB2`. Wire `CS` to `PB2` (Arduino Uno
pin 10) and pass `cs="PB2"`, as the example does.
:::

### MAX7219 methods

| Method | Signature | Description |
|---|---|---|
| `init()` | — | Wake the chip and configure it for matrix use: shutdown off, decode off, intensity 8, scan all 8 rows, display test off |
| `clear()` | — | Write `0x00` to all eight row registers — every LED off |
| `set_row(row, data)` | `row: uint8`, `data: uint8` | Light row `row` (0–7) with the 8-bit pattern `data`; bit set = LED on |
| `set_brightness(level)` | `level: uint8` | Intensity 0 (dimmest) to 15 (brightest). The value is masked with `0x0F` |

That is the whole API. There is no framebuffer, no scrolling, no character or digit rendering —
`set_row()` is the only way pixels get lit, and each call is one two-byte SPI transaction (CS low,
address byte, data byte, CS high).

`row` maps to the MAX7219 digit registers `0x01`–`0x08`, so `set_row(0, …)` writes register `0x01`.
Passing a `row` above 7 writes into the chip's configuration registers instead of the display —
the driver does not range-check it.

### MAX7219 register map

The driver hides these, but they are useful when reading the datasheet next to the source:

| Register | Purpose | Value set by `init()` |
|---|---|---|
| `0x09` | Decode mode | `0x00` — no decode, raw LED control |
| `0x0A` | Intensity | `0x08` — mid brightness |
| `0x0B` | Scan limit | `0x07` — all 8 rows scanned |
| `0x0C` | Shutdown | `0x01` — normal operation |
| `0x0F` | Display test | `0x00` — off |
| `0x01`–`0x08` | Row data | written by `set_row()` / `clear()` |

### Wiring

```text
Arduino Uno          MAX7219 module
-----------          --------------
PB3 (D11)   <-->     DIN   (MOSI)
PB5 (D13)   <-->     CLK   (SCK)
PB2 (D10)   <-->     CS    (SS — see the caution above)
5V          <-->     VCC
GND         <-->     GND
```

A fully lit 8x8 matrix can pull a few hundred milliamps; power the module from the 5 V rail, not
from a GPIO.

## Example

This is the [`max7219` example](https://github.com/PyMCU/pymcu-avr/tree/main/examples/max7219)
from the AVR backend repository, which builds and runs on an Arduino Uno at 16 MHz.

```python
from pymcu.types import uint8
from pymcu.hal.uart import UART
from pymcu.hal.spi import SPI
from pymcu.drivers.max7219 import MAX7219
from pymcu.time import delay_ms


def main():
    uart = UART(9600)
    spi = SPI(cs="PB2")
    mx = MAX7219(spi)

    uart.println("MAX7219")

    mx.init()
    mx.clear()

    uart.println("OK")

    # Checkerboard: alternate 0xAA / 0x55 down the eight rows.
    row: uint8 = 0
    pattern: uint8 = 0xAA
    while row < 8:
        mx.set_row(row, pattern)
        pattern ^= 0xFF
        row += 1

    mx.set_brightness(8)

    delay_ms(500)

    # Animate: row n shows the bit pattern n.
    while True:
        row = 0
        while row < 8:
            mx.set_row(row, row)
            row += 1
        delay_ms(200)
```

Expected UART output at 9600 baud:

```text
MAX7219
OK
```

…with a checkerboard on the matrix, then a shifting pattern.

## Notes

- Call `init()` before anything else. From reset the MAX7219 is in shutdown with decode mode
  undefined, so without it the matrix stays dark or shows garbage.
- `clear()` and `init()` are the expensive calls — eight and five register writes respectively.
  They route through a shared subroutine rather than being force-inlined, so the flash cost is one
  copy plus the argument loads.
- No off-screen buffer. Keep your own `uint8[8]` array if you want to compose a frame before
  displaying it, then push it with eight `set_row()` calls.
- Daisy-chained modules are not supported. The driver emits exactly two bytes per transaction,
  which addresses the first device in a chain only.
