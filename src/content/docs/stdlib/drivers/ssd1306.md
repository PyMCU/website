```python
from pymcu.drivers.ssd1306 import SSD1306
from pymcu.hal.i2c import I2C
```

Driver for the **SSD1306** 128x64 monochrome OLED over I2C. You draw into a RAM framebuffer with
`pixel()`, then push the whole buffer to the panel with `show()`.

`SSD1306` is a **PyMCU stdlib driver**, not part of MicroPython or CircuitPython — neither
ecosystem specifies an SSD1306 class in its core API that PyMCU could mirror, so there is nothing
to switch between and this page shows a single API. You import it exactly as written above
whichever API you use for the rest of your program: a `machine.I2C` sketch and a `busio.I2C`
sketch both say `from pymcu.drivers.ssd1306 import SSD1306`, and it compiles to the same code in
both.

:::caution[This driver costs 1 KB of SRAM]
The framebuffer is a **module-level `uint8[1024]`** — 128 columns × 8 pages. On an ATmega328P
that is **half of the chip's 2 KB of SRAM**, gone the moment you import the module, whether or not
you ever construct an `SSD1306`. Budget for it before you add this driver to a program that also
wants arrays, a `FixedDict`, or a deep call stack.

The buffer is also **shared across every instance**. Two `SSD1306` objects do not get two
framebuffers; they draw into the same 1024 bytes and each `show()` flushes that same content to
its own panel. One display per program is the supported shape.
:::

:::note[AVR only]
The I2C back end lives in `pymcu.drivers._ssd1306.i2c`, so `init()` and `show()` talk to real
hardware on AVR targets. Both dispatch on `__CHIP__.arch` with no other case, so on another
architecture they compile to nothing. `clear()`, `pixel()` and `print_str()` are pure framebuffer
arithmetic and work anywhere — they just have nowhere to be flushed to.
:::

## `SSD1306(i2c, addr)`

| Parameter | Type | Description |
|---|---|---|
| `i2c` | `I2C` | An initialised `pymcu.hal.i2c.I2C` instance |
| `addr` | `uint8` | 7-bit I2C address — `0x3C` on most modules, `0x3D` if the address jumper is moved |

The `i2c` object is a zero-cost abstraction with no runtime representation: it exists to fix the
bus at compile time, and the generated code drives the TWI registers directly.

### SSD1306 methods

| Method | Signature | Description |
|---|---|---|
| `init()` | — | Send the 25-command SSD1306 power-on sequence (charge pump, multiplex ratio, COM config, contrast, display on) |
| `clear()` | — | Zero all 1024 framebuffer bytes. Does **not** touch the panel — call `show()` |
| `pixel(x, y, color)` | `x`, `y`, `color`: `uint8` | Set (`color` non-zero) or clear (`color` zero) one pixel. Coordinates outside 128×64 are ignored |
| `show()` | — | Flush the whole framebuffer to GDDRAM |
| `print_str(x, y, s)` | `x`, `y`: `uint8`, `s`: `str` | Write raw character codes into the framebuffer — see the warning below |

That is the complete list. In particular:

:::danger[`print_str()` is not a text renderer, and there is no `write_char()`]
The module's own header comment tells you to "use `write_char()` after setting cursor" for
"proper 5x7 font rendering". **`SSD1306` has no `write_char()` method** — the comment is stale and
describes something that was never implemented. The five methods in the table above are all there
is.

`print_str(x, y, s)` writes each character's **raw byte value** straight into the framebuffer, one
byte per character, at page row `y >> 3` starting at column `x`. A byte in the framebuffer is a
vertical column of 8 pixels, so the letter `A` (0x41) lights the top and bottom-but-one pixels of
its column. You get a stripe pattern, not readable text. There is **no font table in the stdlib**.

It is genuinely useful as a fast way to blit an 8-pixel-tall bit pattern from a string literal,
which is what it does — just do not expect letters.
:::

`show()` sends the buffer as a **single streaming I2C transaction**: one START, the `0x40` data
control byte, then all 1024 bytes back to back, one STOP. (An earlier version issued a separate
START/STOP per byte — correct, but roughly a thousand times slower.) The AVR `I2C()` back end
clocks TWI at 100 kHz, so a full flush is still on the order of 90 ms: redraw only when something
changed, rather than on every loop iteration.

### Wiring

```text
Arduino Uno          SSD1306 module
-----------          --------------
PC4 (A4)    <-->     SDA
PC5 (A5)    <-->     SCL
5V or 3V3   <-->     VCC   (check your module's regulator)
GND         <-->     GND
```

Most breakout boards already carry the SDA/SCL pull-ups. The default address is `0x3C`.

## Example

This is the [`ssd1306` example](https://github.com/PyMCU/pymcu-avr/tree/main/examples/ssd1306)
from the AVR backend repository, which builds and runs on an Arduino Uno at 16 MHz.

```python
from pymcu.types import uint8
from pymcu.hal.uart import UART
from pymcu.hal.i2c import I2C
from pymcu.drivers.ssd1306 import SSD1306


def main():
    uart = UART(9600)
    i2c = I2C()
    oled = SSD1306(i2c, 0x3C)

    uart.println("OLED")

    oled.init()

    uart.println("OK")

    oled.clear()
    oled.pixel(0, 0, 1)
    oled.pixel(127, 63, 1)

    while True:
        pass
```

Expected UART output at 9600 baud:

```text
OLED
OK
```

…and a lit pixel in the top-left and bottom-right corners of the panel.

:::note
The example lights the corners in the framebuffer but never calls `show()`, so nothing reaches the
panel until you add one. Add `oled.show()` after the two `pixel()` calls to see them.
:::

### Drawing a horizontal line

`pixel()` is the only drawing primitive — everything else is a loop you write yourself.

```python
from pymcu.types import uint8
from pymcu.hal.i2c import I2C
from pymcu.drivers.ssd1306 import SSD1306


def main():
    i2c = I2C()
    oled = SSD1306(i2c, 0x3C)
    oled.init()
    oled.clear()

    x: uint8 = 0
    while x < 128:
        oled.pixel(x, 32, 1)
        x = x + 1

    oled.show()

    while True:
        pass
```

## Notes

- `clear()` clears the buffer, not the panel. Nothing on the display changes until `show()`.
- The buffer layout is `index = (y >> 3) * 128 + x`, bit `y & 7` — the SSD1306's native page
  addressing. `pixel()` does exactly that arithmetic, so it is cheap, but the bounds checks mean
  every call costs two comparisons.
- No font, no shapes, no scrolling helpers. `pixel()` plus your own loops is the whole drawing API.
- 128x64 panels only. The init sequence hard-codes multiplex ratio `0x3F` and COM pin config
  `0x12`; a 128x32 panel needs different values and is not supported.
